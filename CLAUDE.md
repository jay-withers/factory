# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

The front door for every repository under `github.com/jay-withers`. It holds
no application code. You work on the other repos from here, and every change
ships as a PR in the repo it belongs to, through that repo's own CI and
"Protect main" ruleset.

- `repos/<name>`: a clone of every non-archived repo (`make sync`). Treat these
  as read-only mirrors: read and grep them freely, but **never edit or commit
  in them**.
- `worktrees/<name>--<branch>`: where changes happen. Create one with
  `make task REPO=<name> BRANCH=<branch>`.
- `CATALOG.md`: the repo list, generated by `make sync` and imported below.
  For the *why* behind the list (grouping, apply order, what depends on what,
  each repo's required status checks), read
  `repos/github-repos/terraform/terraform.tfvars`. Its comments are the
  canonical catalogue.

@CATALOG.md

## How to work

- One repo, one change: use `/change <repo> <request>`. The same change in
  several repos: use `/sweep <request> [repos | topic:<t> | all]`. Both skills
  spell out the workflow. In short: worktree, read that repo's CLAUDE.md,
  edit, `make lint`/`make test`/`make run` locally, Conventional Commit, push,
  `gh pr create`, `gh pr checks --watch`, merge once green (unless the user
  asked to leave it open), report the URL.
- **Each repo's own CLAUDE.md and README override this file.** Claude Code
  loads a nested CLAUDE.md when you work on files under it, but read it
  explicitly before your first edit in a repo anyway.
- Cross-repo questions ("which repos still pin workflows v1.4?", "what calls
  this reusable workflow?") are answered by searching `repos/`. Run
  `make sync` first if the clones might be stale.
- **Read [docs/delivery.md](docs/delivery.md) before changing CI/CD,
  identities, required checks or Renovate policy in any repo.** It is the
  estate-wide map: what deploys on merge, the `terraform-pending` and
  `deploy-pending` issues that wait for the user, `deploy-failed` issues,
  which checks must always report, and the Azure permission traps (join on
  the shared environment, "whoever applies" RBAC).
  Keep it current when one of those changes.
- `make status` shows uncommitted/unpushed work and every open PR.
  `make clean-worktrees` removes worktrees whose PRs are merged or closed.

## Running apps locally

- From the worktree, use the repo's `make run` (and `make test`). Pass a free
  `PORT=` if another worktree's app is already running. Stop what you start.
- The container talks to the host's Docker (docker-outside-of-docker), so
  `docker build` and `docker compose up` work. VS Code forwards the ports.
- Secrets live in each worktree's gitignored `.env`, copied from its
  `.env.example`. Credentials come from `az login` / `gh auth login` in this
  container. Never commit an `.env`, and never put a secret in a command line
  or PR.
- If an app needs its own dev container exactly, run
  `npx -y @devcontainers/cli up --workspace-folder worktrees/<repo>--<branch>`,
  or hand that folder to the user to open with "Reopen in Container".
- If a repo has no `make run`/`make test` yet, work out how it runs from its
  README, and mention that it's missing the targets.

## Hard rules

These stay human steps. `.claude/settings.json` denies the obvious forms of
each, but the rule applies however the command is spelled:

- Never push to a default branch or force-push. Merging a PR is allowed, but
  only once every required check has passed, as a squash merge
  (`gh pr merge --squash`), and never with `--admin` or any other way round
  the ruleset. Merging deploys: app changes go to dev on their own, and a
  Terraform change opens a `terraform-pending` issue for the user to apply.
- Never run `terraform apply`/`destroy` or `make apply`/`destroy` in any
  repo. A repo with a `cd-terraform` workflow only plans on merge to main
  (through `workflows`' `terraform-deploy.yml`). A plan with changes opens
  a `terraform-pending` issue, and the user applies it by running
  `cd-terraform` from the Actions tab. After the PR merges, watch the plan
  run and report the issue. Never dispatch `cd-terraform` yourself. For any
  other Terraform repo, tell the user to run `make apply`.
  `azure-landingzone` always stays manual.
  `github-repos` uses `cd-terraform` like the rest, as a separate privileged
  identity (see docs/delivery.md).
- Never delete, archive or rename a repo. Adding a repo means a PR to
  `github-repos` adding a `var.repos` entry in `terraform/terraform.tfvars`.
  After the user applies it, `make sync` picks the repo up.

## This repo itself

Built on `template-repo-base`. Its own changes follow the usual flow on a
branch here: Conventional Commits (enforced by commitlint), pre-commit hooks
pinned by SHA (`make lint`), `ci-lint` on PRs (`pre-commit / Pre-commit` is
the required check), and `cd-tag` tagging releases on merge. The scripts
behind the Makefile live in `scripts/`. `make` with no target prints help.
The dev container is the `dev-containers/terraform` image plus
docker-outside-of-docker. It runs `make install` on create and `make sync` on
every start, once `gh` is logged in. Until it is, every new terminal runs
`gh auth login` and `gh auth setup-git` (`scripts/login.sh`, hooked into
`~/.bashrc`). "Logged in" means the token works, not just that one is stored:
a revoked token (HTTP 401) prompts again, while an offline terminal stays quiet.
