# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

The front door for every repository under `github.com/jay-withers`. It holds
no application code. You work on the other repos from here, and every change
ships as a PR in the repo it belongs to, through that repo's own CI and
"Protect main" ruleset.

- `repos/<name>`: a clone of every non-archived repo (`make sync`). Treat these
  as read-only mirrors: read and grep them freely, but **never edit or commit
  in them**. A `SessionStart` hook (`scripts/hooks/session-sync.sh`) runs the
  sync every time a session starts, resumes or is cleared, and reports any
  clone it had to skip. If it says the sync didn't run, the clones may be
  stale.
- `worktrees/<name>--<branch>`: where changes happen. Create one with
  `make task REPO=<name> BRANCH=<branch>`.
- `CATALOG.md`: the repo list, generated by `make sync` and imported below.
  For the *why* behind the list (grouping, apply order, what depends on what,
  each repo's required status checks), read
  `repos/github-repos/terraform/terraform.tfvars`. Its comments are the
  canonical catalogue.

@CATALOG.md

## How to work

- One repo, one change: use `/change <repo> <request>`. The same change in
  several repos: use `/sweep <request> [repos | topic:<t> | all]`. Both skills
  spell out the workflow. In short: worktree, read that repo's CLAUDE.md,
  edit with tests (a fix gets a regression test), update the docs it makes
  false, `make test`/`make run` locally, review the diff with the `code-review` skill, `../../scripts/verify.sh`,
  Conventional Commit, push, `gh pr create`, `gh pr checks --watch`, merge
  once green (unless the user asked to leave it open), report the URL.
- **Nothing ships from a worktree unverified.** A `PreToolUse` hook in
  `.claude/settings.json` (`scripts/hooks/require-verified.py`) blocks
  `git push` and `gh pr create` under `worktrees/` unless HEAD's tree is the
  one `scripts/verify.sh` last passed (lint, docs check, tests). Changed
  something since? Verify again. Never work round it.
- **A change ships with its docs.** In the same PR, update every doc it
  makes false: the repo's README, CLAUDE.md and `docs/`, plus any other
  repo's docs that describe it. Put factory's own docs (`docs/`, this file,
  the README, the skills) in a companion PR from
  `make task REPO=factory BRANCH=docs/<slug>`. Every PR body carries a
  **Docs** line saying what changed or why nothing needed to. `verify.sh`
  runs `scripts/docs-check.py`, which fails on links, paths and `make`
  targets the change broke. Stale prose is on you: /change step 5 says
  where to look. `make docs-check` audits every clone.
- **Each repo's own CLAUDE.md and README override this file.** Claude Code
  loads a nested CLAUDE.md when you work on files under it, but read it
  explicitly before your first edit in a repo anyway.
- Cross-repo questions ("which repos still pin workflows v1.4?", "what calls
  this reusable workflow?") are answered by searching `repos/`. Run
  `make sync` first if the clones might be stale.
- **Read [docs/delivery.md](docs/delivery.md) before changing CI/CD,
  identities, required checks or Renovate policy in any repo.** It is the
  estate-wide map: what deploys on merge, the `terraform-pending` and
  `deploy-pending` issues that wait for the user, `deploy-failed` and
  `build-failed` issues,
  which checks must always report, and the Azure permission traps (join on
  the shared environment, "whoever applies" RBAC).
  Keep it current when one of those changes.
- **[docs/autonomy.md](docs/autonomy.md) says when to ask and when to just
  proceed.** Default to proceeding: the guardrails above catch mistakes.
- **[docs/repo-standard.md](docs/repo-standard.md) is the shape every repo
  should have.** Build new repos to it, and use it to tell a deliberate
  exception from drift.
- **[docs/architecture.md](docs/architecture.md) is the estate's
  architecture as a talk-through deck**: Mermaid diagrams of how the pieces
  connect, with speaker notes. Update the slide a change makes false (a new
  or removed repo, shared resource, dependency, trust path or delivery
  stage). Its estate map must name every repo in `CATALOG.md`:
  `scripts/architecture-check.py` checks that at every session sync, in
  `make docs-check` and in `verify.sh` for factory, and the sync hook
  reports a mismatch as `deck check:`.
- **[docs/greenfield.md](docs/greenfield.md) is the apply order for
  rebuilding the estate in a new tenant**, with every literal tied to the
  current tenant. A new tenant-bound literal belongs in its table.
- `make status` shows uncommitted/unpushed work and every open PR.
  `make clean-worktrees` removes worktrees whose PRs are merged or closed.

## Running apps locally

- From the worktree, use the repo's `make run` (and `make test`). Pass a free
  `PORT=` if another worktree's app is already running. Stop what you start.
- Tools come from mise: jay-withers/toolchain sets a machine up once, and
  each repo's `mise.toml` pins its own versions (`make install` runs
  `mise install`). `docker build` and `docker compose up` use the machine's
  Docker.
- Secrets live in each worktree's gitignored `.env`, copied from its
  `.env.example`. Credentials come from `az login` / `gh auth login` in this
  container. Never commit an `.env`, and never put a secret in a command line
  or PR.
- If a repo has no `make run`/`make test` yet, work out how it runs from its
  README, and mention that it's missing the targets.

## Hard rules

These stay human steps. `.claude/settings.json` denies the obvious forms of
each, but the rule applies however the command is spelled:

- Never push to a default branch or force-push. Merging a PR is allowed, but
  only once every required check has passed, as a squash merge
  (`gh pr merge --squash`), and never with `--admin` or any other way round
  the ruleset. Merging deploys, but only Renovate's routine releases go to
  dev on their own. A release a person merged (yours included) opens a
  `deploy-pending` issue, and the user runs `cd-publish` with its tag. A
  Terraform change opens a `terraform-pending` issue for the user to apply.
- Never run `terraform apply`/`destroy` or `make apply`/`destroy` in any
  repo. A repo with a `cd-terraform` workflow only plans on merge to main
  (through `workflows`' `terraform-deploy.yml`). A plan with changes opens
  a `terraform-pending` issue, and the user applies it by running
  `cd-terraform` from the Actions tab. After the PR merges, watch the plan
  run and report the issue. Never dispatch `cd-terraform` yourself. For any
  other Terraform repo, tell the user to run `make apply`.
  `azure-landingzone`'s `bootstrap` component always stays manual; its other
  components, and `github-repos`, use `cd-terraform` like the rest, each as a
  privileged identity in a main-only `apply` environment (see
  docs/delivery.md).
- Never delete, archive or rename a repo. Adding a repo means a PR to
  `github-repos` adding a `var.repos` entry in `terraform/terraform.tfvars`.
  After the user applies it, `make sync` picks the repo up.

## This repo itself

Built on `template-repo-base`. Its own changes follow the usual flow on a
branch here: Conventional Commits (enforced by commitlint), pre-commit hooks
pinned by SHA (`make lint`), `ci-lint` on PRs (`pre-commit / Pre-commit` is
the required check), and `cd-tag` tagging releases on merge. The scripts
behind the Makefile live in `scripts/`, with unit tests in `scripts/tests/`
(`make test`). Two local pre-commit hooks run those tests and check that
this repo's Markdown links and heading anchors still resolve. `make` with no target prints help.
There is no dev container: `mise.toml` pins the tools and `make install` runs
`mise install`. `.vscode/extensions.json` recommends the extensions for the
whole estate, since VS Code reads only the workspace root's file, not the
copies in `repos/` and `worktrees/`. `.vscode/tasks.json` runs `make sync`
each time the folder opens, once `gh` is logged in. `make login`
(`scripts/login.sh`) runs `gh auth login` and `gh auth setup-git`, then
syncs. "Logged in" means the token works, not just that one is stored: a
revoked token (HTTP 401) prompts again, while an offline terminal stays quiet.
